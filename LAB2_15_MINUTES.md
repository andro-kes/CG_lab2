# Лаба №2: от кнопки до освещённого конуса

**Цель на 15 минут:** понять, что происходит после нажатия кнопки, откуда берётся цвет поверхности и в каком файле это изменить. Читай основной разбор по порядку. Для работы с открытой программой перейди к [подробной карте интерфейса](#подробная-карта-интерфейса): там описаны все кнопки и настройки с функциями и номерами строк. Основной разбор остаётся отдельным маршрутом на 15 минут, а карта интерфейса служит справочником.

## 1. Сначала представь результат — 1 минута

Ты видишь конус, окно настроек и маленькие кубики-лампы. За этим стоят две части программы:

- **Процессор, CPU:** выполняет C++-код. Хранит параметры, обрабатывает кнопки и передаёт данные видеокарте.
- **Видеокарта, GPU:** выполняет шейдеры. Определяет, где рисовать поверхность и каким цветом её закрасить.

Шейдер — небольшая программа для GPU. В этой лабе вершинный шейдер обрабатывает вершины треугольников, фрагментный — участки поверхности, которые могут попасть в пиксели экрана.

Представь один такой участок конуса. Чтобы вычислить его цвет, нужны четыре вещи: **где он находится, куда повёрнут, какой у него материал и откуда приходит свет**. Почти весь код второй лабы готовит эти данные или использует их.

Теперь нажмём **Add point** и проследим весь путь новой лампы.

## 2. Нажали Add point: что именно произошло — 3 минуты

### Шаг 1. В памяти программы появился ещё один источник

Открой `source/application.cpp`, функцию `pointLightsUi()`:

```cpp
auto& lights = controls.lighting.points;
if (ImGui::Button("Add point")) {
    PointLight light;
    light.position.x += 0.3f * float(lights.size() % 6);
    lights.push_back(light);
}
```

Прочитаем буквально:

1. `auto& lights` — короткое имя для существующего списка точек. Знак `&` означает, что работаем с самим списком, а не с его копией.
2. `ImGui::Button(...)` показывает кнопку и возвращает `true`, если её нажали.
3. `PointLight light;` создаёт источник с начальными настройками из `scene.hpp`: положением, цветом и интенсивностью.
4. Следующая строка немного сдвигает его по X. `% 6` даёт остаток от деления: сдвиг повторяется через шесть источников.
5. `push_back()` добавляет источник в конец списка. `std::vector` — массив, который умеет увеличиваться.

Пока появилась только запись с числами. Сам по себе C++-объект `PointLight` ничего не рисует.

### Шаг 2. Настройки превращаются в данные для GPU

Ниже, в `application::render()`, выполняется:

```cpp
scene.light_counts = glm::uvec4(lighting.points.size(), lighting.spots.size(), 0, 0);
```

В первое число записывается количество точек, во второе — прожекторов. Это скажет шейдеру, сколько источников обходить.

Далее для каждой точки создаётся запись:

```cpp
points.push_back({glm::vec4(light.position, 1),
                  glm::vec4(light.color, light.intensity)});
```

`vec4` содержит четыре числа. Например, цвет `(1, 0.5, 0)` и интенсивность `8` упаковываются в `(1, 0.5, 0, 8)`. Четвёртое число обозначается `.w`.

**Зачем отдельная структура `PointLightGpu`?** CPU и шейдер должны одинаково понимать, где в памяти лежат позиция, цвет и интенсивность. Их общий формат описан в `gpu_data.hpp` и повторён в GLSL.

### Шаг 3. Данные попадают в буфер

`graphics::renderScene()` из `graphics.cpp` вызывает `ensureBufferSize()`, затем `writeBuffer()`.

Буфер — участок памяти, доступный GPU. Первая функция проверяет, хватает ли места, и при необходимости создаёт больший буфер. Вторая копирует туда числа. Обращение `vmaFlushAllocation()` обеспечивает видимость записи для GPU там, где это требуется свойствами памяти.

### Шаг 4. Шейдер учитывает новую лампу

В `shaders/cone.frag` есть цикл:

```glsl
for (uint i = 0; i < scene.lightCounts.x; ++i) {
    PointLight light = points.lights[i];
    // Далее вычисляется и прибавляется вклад этого источника.
}
```

Комментарий здесь поясняющий; полный расчёт разберём ниже. Было две точки — цикл выполнялся два раза для каждого обрабатываемого фрагмента. Добавили третью — выполняется три раза.

**Вот вся связь кнопки с картинкой:** вырос список на CPU, обновились счётчик и буфер, шейдер прибавил ещё один вклад света. Переписывать или пересоздавать сам шейдер при добавлении лампы не требуется.

## 3. Что освещаем: треугольники и нормали — 2 минуты

Видеокарте передаётся конкретная геометрия. В `cone_mesh.hpp` одна вершина описана так:

```cpp
struct ConeVertex {
    glm::vec3 position;
    glm::vec3 color;
    glm::vec3 normal;
};
```

`vec3` — три числа. У `position` это x, y, z. У `color` — красная, зелёная и синяя составляющие. `normal` задаёт направление поверхности.

`makeConeMesh()` делит окружность на 64 сектора. В каждом строит боковой треугольник и треугольник основания: всего **128 треугольников**. `sin` и `cos` дают точки на окружности, а список индексов задаёт порядок соединения вершин.

**Нормаль можно представить как короткую стрелку, торчащую из поверхности под прямым углом.** Повернули поверхность к лампе — она обычно освещена сильнее. Повернули боком — слабее. Стрелка позволяет выразить это числами.

У основания конуса нормаль смотрит вниз: `(0, -1, 0)`. На боковой поверхности — наружу и немного вверх. В коде направление получается из `(cos(a), radius / height, sin(a))`.

`normalize()` делает длину стрелки равной 1, сохраняя направление. Иначе яркость могла бы зависеть ещё и от случайной длины нормали.

На ребре основания координаты двух вершин могут совпадать, а нормали — различаться. Поэтому основание и бок используют отдельные вершины: это сохраняет резкую границу между поверхностями. В верхушке нормаль выбирается отдельно для каждого сектора как среднее соседних боковых направлений.

## 4. Как вершина попадает на экран — 2 минуты

Координаты вершины сначала заданы относительно самого конуса. Но конус можно передвинуть, а камеру — повернуть. Для этого используются матрицы: таблицы чисел, описывающие преобразования.

| Матрица | Простыми словами | Пример изменения |
| --- | --- | --- |
| `M`, model | Разместить объект в общей сцене | Передвинуть конус вправо |
| `V`, view | Посмотреть на сцену из камеры | Обойти конус с другой стороны |
| `P`, projection | Получить проекцию на плоскость | Изменить угол обзора |

В `application.cpp` функция `makeModel()` собирает `M` из положения, поворотов и масштаба. `makeViewProjection()` собирает `P * V`.

Две строки из `cone.vert`:

```glsl
vec4 world = object.model * vec4(inPosition, 1.0);
gl_Position = scene.viewProjection * world;
```

Первая переводит вершину в общую сцену. Например, локальная точка `(1, 0, 0)` после переноса объекта на `(3, 0, 0)` окажется в `(4, 0, 0)`.

Вторая применяет камеру и проекцию. Общая запись — **`P * V * M * position`**. Применяем справа налево: сначала объект, затем камера, затем проекция. `gl_Position` ещё не содержит номер пикселя: дальнейшее преобразование в экранные координаты выполняет GPU.

У камеры `yaw` отвечает за взгляд влево-вправо, `pitch` — вверх-вниз. `cameraForward()` превращает углы в направление; `lookAtRH()` строит матрицу вида.

`fov` — вертикальный угол обзора перспективной камеры. Увеличил его — видно больше пространства. В перспективе далёкие предметы выглядят меньше. В ортографической проекции размер от удаления не меняется.

Строка `projection[1][1] *= -1` согласует направление Y с используемым выводом Vulkan. Проекции с суффиксом `ZO` дают нужный диапазон глубины от 0 до 1.

**Отдельная тонкость — нормали.** Если растянуть объект по X сильнее, чем по Y, обычное умножение нормали на `M` может нарушить её перпендикулярность поверхности. Поэтому CPU вычисляет:

```cpp
model.normal_matrix = glm::transpose(glm::inverse(model.model));
```

Обратная транспонированная матрица нужна именно для корректного направления нормали при таком масштабе. Заучивать её вывод для чтения этого кода не требуется; нужно понимать причину применения.

## 5. Как из направлений получается цвет — 4 минуты

Между вершинами треугольника GPU вычисляет промежуточные координаты, цвета и нормали. Это называется интерполяцией. Фрагментный шейдер получает эти значения и рассчитывает освещение каждого фрагмента отдельно.

### Материал: что за поверхность перед нами

В `scene.hpp` структура `Material` хранит:

- `albedo` — основной цвет поверхности;
- `specular` — цвет блика;
- `shininess` — насколько узким будет блик;
- `vertex_colors` — нужно ли дополнительно умножать цвет на цвета вершин из первой лабы.

Для начала мысленно выключи блики: поставь `Specular color` в чёрный. Так проще понять обычное освещение.

### Diffuse: насколько поверхность обращена к лампе

В `blinnPhong()` есть строка:

```glsl
float diffuse = max(dot(N, L), 0.0);
```

`N` — единичная нормаль. `L` — единичное направление **от поверхности к лампе**. `dot(N, L)` показывает, насколько совпадают эти направления:

| Положение лампы относительно нормали | Значение |
| --- | --- |
| Прямо по направлению нормали | 1 — максимальный вклад |
| Угол между `N` и `L` равен 60° | 0,5 — половина |
| Угол 90° | 0 — свет идёт вдоль поверхности |
| Лампа с обратной стороны | Отрицательное число; `max` заменяет его нулём |

Это скалярное произведение. Для единичных векторов оно равно косинусу угла. Вся практическая идея: **чем сильнее поверхность повернута к свету, тем больше diffuse**.

### Расстояние: почему далёкая лампа светит слабее

Для точки шейдер вычисляет:

```glsl
vec3 delta = light.position.xyz - worldPosition;
float distanceSquared = max(dot(delta, delta), 0.0001);
vec3 radiance = light.colorIntensity.rgb * light.colorIntensity.w / distanceSquared;
```

`delta` — вектор от поверхности к лампе. Его скалярное произведение с самим собой даёт квадрат длины, то есть `r²`. Последняя строка делит цвет и интенсивность света на `r²`.

Учебный пример: интенсивность равна 8. На расстоянии 2 множитель света равен `8 / 4 = 2`. На расстоянии 4 — `8 / 16 = 0,5`. При удвоении расстояния вклад уменьшился в четыре раза. Угол поверхности при этом считаем неизменным.

`0.0001` защищает от деления на ноль в позиции источника. `safeNormalize(delta)` даёт направление `L` с защитой для нулевого вектора.

### Specular: откуда берётся яркое пятнышко

Теперь верни ненулевой `Specular color`. В расчёт включается направление `V` — от поверхности к наблюдателю:

```glsl
vec3 H = safeNormalize(L + V);
float specular = pow(max(dot(N, H), 0.0), object.specular.w);
```

`H` смотрит посередине между направлением на лампу и направлением на наблюдателя. Когда нормаль близка к `H`, получается сильный блик. Это и есть используемый подход Блинна—Фонга.

`pow` возводит число в степень `shininess`. Например, `0.8² = 0,64`, а `0.8³² ≈ 0,0008`. При большой степени яркими остаются только места с почти идеальным совпадением направлений — блик становится узким.

**Поэтому при движении камеры блик перемещается:** меняется `V`, вслед за ним `H`. Обычный diffuse от положения камеры не зависит. В перспективе `V` рассчитывается к позиции камеры; в ортографии направление взгляда одинаково для всех фрагментов.

Если лампа за поверхностью, функция сразу возвращает нулевой вклад: блик с этой стороны тоже не добавляется.

### Остальные источники и итог

**Ambient** — постоянная фоновая подсветка: `base * scene.ambient.rgb`. Она добавляется один раз и помогает не оставлять неосвещённые участки полностью чёрными. Переотражения света между объектами здесь не рассчитываются.

**Направленный свет** похож на очень далёкий источник: направление одинаково во всей сцене, затухания по расстоянию нет. В интерфейсе `direction` показывает, куда свет идёт. Формуле нужен вектор к источнику, поэтому берётся `-direction`.

**Прожектор** рассчитывается как точечный источник с дополнительным ограничением по углу. Внутри внутреннего конуса свет полный, за внешним — нулевой, между ними плавно уменьшается:

```glsl
coneFactor = clamp((theta - outerCos) / (innerCos - outerCos), 0.0, 1.0);
```

`theta` здесь — косинус угла между осью прожектора и направлением от него к поверхности. Например, при `innerCos = 0,95`, `outerCos = 0,85`, `theta = 0,90` коэффициент равен `0,5`. `clamp` удерживает результат между 0 и 1. При равных или почти совпадающих косинусах код использует отдельную проверку границы, чтобы избежать деления на ноль.

В интерфейсе задаются полууглы — от оси до края конуса. `application::render()` заранее вычисляет их косинусы для GPU.

В итоге шейдер складывает **фон + направленный свет + вклады всех точек + вклады всех прожекторов**. У каждого источника учитываются материал, diffuse и блик. Слишком большая сумма даёт пересвет; это повод уменьшить интенсивности.

## 6. Зачем столько Vulkan-кода — 2 минуты

Формула света короткая. Vulkan-код обеспечивает её выполнение с правильными данными и в правильный момент.

| Термин | Что это в нашей программе | Зачем нужен |
| --- | --- | --- |
| Buffer | Память с вершинами, матрицами или источниками | GPU читает из неё данные |
| Descriptor | Запись о том, где лежит нужный буфер | Шейдер находит свои данные |
| Descriptor set | Группа таких записей | Подключить данные сцены или объекта |
| Pipeline | Шейдеры и настройки рисования | Задать обработку вершин, треугольников, линий и глубины |
| Command buffer | Список записанных команд | Передать GPU последовательность работы |
| Swapchain | Набор изображений для вывода | Получить изображение, нарисовать его и показать |

В `createDescriptors()` данные разделены на две группы. **Set 0** содержит сцену: камеру, общий свет и два массива источников. **Set 1** содержит объект: его преобразование и материал.

Сцена и объект записываются в uniform-буферы фиксированного размера. Массивы света — в storage-буферы: в шейдере у них объявлено `lights[]`, а число используемых элементов передаётся отдельно.

CPU и GLSL должны совпадать не только по порядку полей, но и по их расположению в байтах. `std140` и `std430` задают правила в GLSL; `alignas(16)` и проверки `static_assert` помогают согласовать структуры C++. Если размещение различается, шейдер может прочитать чужое число вместо интенсивности.

`renderScene()` записывает очистку кадра, подключение данных и рисование. `vkCmdDrawIndexed()` рисует конус по индексам, `vkCmdDraw()` — маркеры. Проверка глубины оставляет видимыми ближайшие поверхности.

**Почему перед обновлением буфера ждём fence?** Предыдущий кадр мог ещё читать этот буфер. Перезапись в этот момент смешала бы старые и новые данные. В нашей простой реализации одновременно выполняется один кадр; fence позволяет CPU дождаться его завершения. Семафоры связывают готовность изображения, рисование и показ.

В `main.cpp` функция `run()` повторяет: события окна, `prepare()`, интерфейс и `update()`, подготовку сцены через `render()`, отправку и показ через `submitAndPresent()`. Команды ImGui рисуют панель поверх сцены. При изменении размера пересоздаётся swapchain; при выходе ресурсы освобождаются через `cleanup`.

## 7. Проверь, что связал всё вместе — 1 минута

**Ты выключил Show light markers. Почему конус всё ещё освещён?**

Кубики — только обозначения. `makeLightMarkers()` перестал создавать их геометрию, но источники остались в массиве, который читает `cone.frag`. `marker.frag` просто выводит цвет кубика и сам свет не рассчитывает.

**Ты растянул конус по одной оси. Что защищает освещение от искажения?**

Обратная транспонированная матрица нормалей и их нормализация перед расчётом света.

**Ты нажал Play. Где появляется движение?**

В `animation.hpp` время увеличивает `phase`, а синусы дают смещения и повороты. `makeModel()` включает их в матрицу объекта. Сами исходные вершины конуса перестраивать не нужно.

**Ты удалил все точки. Почему шейдер не читает лишнюю память?**

Счётчик точек стал нулевым, поэтому цикл не выполняется. GPU-буфер при этом остаётся ненулевого размера. Удаление отдельного элемента выполняется после построения списка ImGui, чтобы не повторять ID элементов внутри одного кадра.

### 4. Animation: что двигается, а что сбрасывается

**Как открыть:** `Object and material`, затем `Animation`. **Реализация:** часть `modelUi()`. Переменная `animation` — ссылка на `controls.animation`.

| Элемент и строка | Что делает | Поле или действие |
| --- | --- | --- |
| **Play / Pause**, 73 | Одна кнопка с меняющейся надписью. `Play` запускает изменение фазы, `Pause` останавливает его в текущем положении. Повторный Play продолжает движение. | `animation.playing = !animation.playing` |
| **Reset motion**, 75 | Останавливает анимацию и возвращает её фазу в ноль. Ручные Position, Rotation и Scale сохраняются, как и настройки скорости и амплитуд. | `animation.phase = 0; animation.playing = false;` |
| **Speed**, 76 | Множитель скорости 0,1…3. При 2 фаза изменяется вдвое быстрее, чем при 1. | `animation.speed` |
| **Path radius**, 77 | Размер анимационного смещения по X: 0…1,5. Несмотря на название, в текущей формуле это амплитуда X, а не радиус круговой орбиты. | `animation.radius` |
| **Vertical range**, 78 | Амплитуда движения по Y: 0…1. При значении 0,5 анимационная добавка меняется от −0,5 до +0,5. | `animation.height` |
| **Depth range**, 79 | Амплитуда движения по мировой оси Z: 0…1. После поворота камеры эта ось не обязательно направлена в глубину экрана. | `animation.depth` |

**Где реализовано движение:** `source/animation.hpp`. `advanceAnimation()` изменяет фазу, а `animationPose()` вычисляет:

```cpp
x = radius * sin(t);
y = height * sin(2 * t);
z = depth * sin(3 * t);
```

Это сокращённая запись формул из функции. Там же рассчитываются повороты. `makeModel()` добавляет результат к ручным настройкам конуса.

Запомни разницу: **Pause** сохраняет текущую фазу; **Reset motion** возвращает анимационную добавку в начало; **Reset all** возвращает исходные настройки всей сцены.

### 5. Ambient and directional light: общий и направленный свет

**Реализация:** `globalLightUi()`. Переменная `lighting` — ссылка на `controls.lighting`.

| Элемент и строка | Что делает | Поле данных |
| --- | --- | --- |
| **Ambient color**, 86 | Цвет постоянной фоновой подсветки поверхности. | `lighting.ambient_color` |
| **Ambient intensity**, 87 | Сила фоновой подсветки: 0…1. При нуле этот вклад выключается. | `lighting.ambient_intensity` |
| **Direction**, 88 | Направление распространения направленного света. Три компоненты от −10 до 10. Например, `(0, -1, 0)` означает свет сверху вниз. | `lighting.direction` |
| **Directional color**, 89 | Цвет направленного света; влияет на diffuse и блик от него. | `lighting.directional_color` |
| **Directional intensity**, 90 | Интенсивность направленного света: 0…3. При нуле он не даёт вклада. | `lighting.directional_intensity` |

`Direction` — вектор направления, его компоненты не являются углами в градусах. Перед отправкой в шейдер он нормализуется. Поэтому `(0, -1, 0)` и `(0, -5, 0)` задают одно направление. Нулевой или очень маленький вектор заменяется направлением вниз `(0, -1, 0)` через `normalizedOr()` из `scene.hpp`.

**Путь в коде:** `application::render()` готовит `scene.ambient`, `scene.light_direction` и `scene.light_color`. В `cone.frag` ambient добавляется один раз, направленный свет — отдельным вызовом `blinnPhong()` с противоположным направлением `-scene.lightDirection.xyz`.

Чтобы увидеть действие только одной точки, можно поставить обе общие интенсивности в ноль и убрать прожекторы. Простое сворачивание этого раздела свет не выключает.

| **Outer angle**, 144 | Внешний полуугол, за которым света нет. Диапазон от текущего Inner angle до 80°. При увеличении расширяется общий конус освещения. | `light.outer_angle` |

**Как понимать углы:** при Inner angle = 15° и Outer angle = 25° область полного света имеет полный угол 30°, а весь конус — 50°. Между двумя границами идёт плавный переход. При равных углах граница получается резкой.

**Как работает Aim at object:** `makeModel()[3]` — столбец переноса матрицы объекта. Из него берётся положение центра конуса. Затем вычитается позиция прожектора — получается направление к цели. После последующего перемещения объекта или прожектора нажми кнопку ещё раз, если нужно новое наведение. Постоянного слежения кнопка не включает.

**Где это применяется:** `application::render()` нормализует направление, вычисляет косинусы углов и создаёт `SpotLightGpu`. В `cone.frag` цикл по `scene.lightCounts.y` вычисляет `coneFactor` и вклад прожектора. `addSpotCone()` в `light_markers.hpp` отдельно строит линии по тем же углам. Длина этих линий фиксирована и не задаёт дальность света.

### Как прочитать строку ImGui и самому изменить настройку

Возьмём реальную строку из `pointLightsUi()`:

```cpp
ImGui::SliderFloat("Intensity", &light.intensity, 0, 100, "%.2f", ImGuiSliderFlags_AlwaysClamp);
```

| Часть вызова | Значение |
| --- | --- |
| `SliderFloat` | Создать ползунок для одного дробного числа. |
| `"Intensity"` | Надпись в интерфейсе; по ней удобно искать строку. |
| `&light.intensity` | Адрес изменяемого поля. ImGui записывает новое число прямо в эту переменную. |
| `0, 100` | Минимальное и максимальное значение. Чтобы изменить допустимый диапазон, правь эти аргументы. |
| `"%.2f"` | Показывать две цифры после десятичной точки. Это формат отображения. |
| `AlwaysClamp` | Удерживать значение внутри границ, в том числе при ручном вводе. |

У `DragFloat3` после адреса поля есть ещё **скорость изменения мышью**. Например, в `Position` точки число `0.03f` задаёт чувствительность перетаскивания, а следующие `-20, 20` — допустимые границы.

`Button` возвращает признак нажатия, и действие написано рядом в `if`. `Checkbox` получает адрес переменной `bool` и меняет её. `ColorEdit3` меняет три компоненты цвета. `Combo` меняет номер выбранного варианта. Функции с окончанием `Ui()` управляют данными CPU; отправка обновлённых значений на GPU выполняется далее через `application::render()`.

| Включил Show spotlight cones, но линий нет | Включи также Show light markers и проверь, что есть хотя бы один прожектор. |
| Удалил все точки, а свет остался | В сцене могут работать ambient, направленный свет и прожекторы. |
| Прожектор не освещает объект | Проверь его Intensity, нажми Aim at object и увеличь Outer angle. Угол освещения и обращённость поверхности к источнику тоже влияют на результат. |
| Нажал Aim at object, затем запустил анимацию, и свет ушёл с конуса | Наведение выполнялось однократно. Повторно нажми кнопку для текущего положения. |
| Сделал Albedo чёрным, но вижу блик | У блика отдельный Specular color. Для удаления этого вклада сделай его чёрным. |
| Меняю Shininess, но разницы почти нет | Нужен ненулевой Specular color и подходящее взаимное положение камеры, света и поверхности. Сравни сильно различающиеся значения, например 8 и 128. |
| После Reset motion объект не в начале мировых координат | Сброшена только анимация. Ручные Position и Rotation сохраняются; полный сброс делает Reset all. |

### Короткий маршрут демонстрации после сборки

1. Нажми **Reset all**, затем раскрой **Camera**. Измени Yaw и Field of view, верни Reset camera. В коде покажи `cameraUi()` и `makeViewProjection()`.
2. Раскрой **Object and material**. Поменяй Albedo, сравни Shininess 8 и 128, измени одну компоненту Scale. Покажи `modelUi()`, `makeModel()` и `blinnPhong()`.
3. Для отдельного показа точек поставь **Ambient intensity** и **Directional intensity** в 0, нажми **Remove all spots**. Раскрой **Point 1**, поменяй Position, Color, Intensity, затем нажми **Add point**. Покажи `pointLightsUi()` и цикл точек в `cone.frag`.
4. Нажми **Remove all points**, затем **Add spot** и **Aim at object**. Сравни разные Inner angle и Outer angle. Покажи `spotLightsUi()` и расчёт `coneFactor`.
5. Сними **Show light markers**: освещение сохраняется. Затем включи маркеры, открой **Animation**, нажми **Play**, **Pause**, **Reset motion**. Объясни разницу между данными света, его обозначениями и анимацией объекта.

Линии прожектора показывают внутренний и внешний углы. Их фиксированная длина не означает, что свет дальше обрывается. `Aim at object` направляет прожектор на объект один раз; слежения за анимацией эта кнопка не включает.

### Объяснение для защиты за полминуты

«Конус построен процедурно из треугольников. Для вершин вычислены нормали. CPU обрабатывает интерфейс, рассчитывает матрицы и передаёт данные через uniform- и storage-буферы. Вершинный шейдер преобразует геометрию, а фрагментный считает Блинна—Фонга в мировых координатах. Точки и прожекторы хранятся в динамических массивах. Они ослабевают как 1/r², у прожектора есть плавный переход между двумя углами. Источники показаны отдельными неосвещаемыми маркерами».

Тени от перекрытия света объектами здесь не рассчитываются: нулевой `dot(N,L)` учитывает только ориентацию поверхности.

### Сборка и проверка

`build.cmd --offline` собирает проект с доступными зависимостями. CMake запускает `glslc`, который переводит GLSL в `.spv`; `run.cmd` запускает программу с нужными путями к DLL и validation layers. Последние выводят ошибки использования Vulkan в консоль.

Разбор относится к исходникам после ревью. Четыре шейдера прошли компиляцию и `spirv-val`; пересборка C++ в рабочем окружении остановилась на `clang-23: Permission denied`. Старый EXE от 21.10.2026 не содержит последних правок. Их список — в `REVIEW.md`.
